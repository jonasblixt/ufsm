# Code review: architecture and cognitive load (2026-10-11)

Scope: the TypeScript rewrite on `ts-rewrite` at commit `ee35b9e`: `packages/core`, `packages/cli`, `apps/editor`, the
tests and the docs. `old/` is out of scope. The review looks at architecture, domain boundaries and how the code is
partitioned, and asks one question throughout: **what does a developer new to the team have to hold in their head to
make a change safely, and how can that be reduced?** Bugs are reported where they turned up along the way, but finding
bugs was not the goal.

How it was done: I read the core pipeline end to end (model, index, structure, flatten, flat runner, lowering, IR,
interpreter, all four printers), the diagram layer (geometry, route, edit, create, props, check), the editor's
`main.ts`, `panel.tsx`, `render.ts`, `history.ts`, `fsm/input.ts`, the CLI, the test layout, CI and the docs. I
extracted the import graph inside core and probed one suspected gap with a small script and the CLI (section 4). I did
not run the full test suite.

---

## 1. Summary

The core is in good shape. The pipeline (model → structure → flat tables → IR → printers) is a sound design, the
layers are documented at the top of every file, semantics are written down normatively, and the verification story
(hand-derived traces, differential runs against an interpreter on random models, warning-free generated code in four
languages) is better than most commercial code generators have. The comment discipline is unusually high.

The cognitive load comes from five places:

1. **The editor's `main.ts` is a 2,306-line module** that owns almost all editor state in 30 module-level variables
   and wires everything to everything. It is the first file a newcomer opens and the hardest one to change.
2. **`@ufsm/core` has no public surface and no internal boundaries a reader can see.** 406 exports in one flat
   namespace via `export *`; the `v1/` folder holds three different domains (file format, diagram layout, editing
   operations); a few modules sit in the wrong layer (the shared runtime contract lives inside the interpreter, shared
   codegen helpers live inside the C backend).
3. **Duplication across the four backends.** Each printer is one 600–860-line function, and each repeats the same IR
   analysis (statement walk, reachability, fallibility, queue/terminate detection). Adding a fifth language means
   copying it again; changing the analysis means changing it four times.
4. **"Is this model valid?" is answered in four places** (design rule check, structure builder, flattener, editor
   pre-checks), with five error classes. A model can pass `ufsm check` and then crash `ufsm generate` (section 4).
5. **The project's knowledge is written for an AI, not for a person.** The architecture overview, the file map and
   the conventions live in `.claude/CLAUDE.md` and `.claude/rules/*.md`; the "why" lives in a 66 KB decisions log.
   There is no `docs/architecture.md`, no glossary, and several core words are overloaded ("trace" means four things).

None of these needs a rewrite. Section 6 gives a sequence of small, independently landable refactorings, ordered by
payoff per effort.

---

## 2. What is good and should be kept

These are deliberate strengths; the refactoring plan is designed not to disturb them.

- **One pipeline, decided once.** `docs/semantics.md` defines behaviour; the interpreter implements it; the lowering
  (`ir/lower.ts`) makes every decision so printers only print. The rule "backends make no semantic decisions" is the
  single most valuable architectural rule in the repository.
- **Platform-neutral core.** No Node or DOM in `packages/core/src`; the editor, CLI and tests run the same code.
- **The document is the only state.** Every edit is a core function run on an Immer draft (`history.ts`); index,
  geometry and handles are derived. Undo/redo falls out for free and the edit functions are unit-testable without a
  DOM. `PanelOps` (`panel.tsx:95`) is a clean, narrow contract between the panels and the document.
- **Stored vs derived is explicit.** S routes, action blocks and sheet frames store only what the user pinned;
  everything else is derived in core (`route.ts`, `action-block.ts`, `sheet.ts`).
- **Verification.** Conformance traces are data, replayed against every backend; random models drive differential
  runs; generated code is held to `-Werror`, `pyright --strict`, clippy pedantic and rustfmt. The planted-bug check
  shows the tests actually catch semantic mistakes.
- **One schema source** (`v1/schema.ts`, TypeBox) that drives the reader, generates the JSON Schema, and is checked
  against `model.ts` at compile time.
- **File headers that explain the module's role.** `structure.ts`, `flatten.ts`, `ir.ts` and `lower.ts` each open with
  the concepts the file introduces. That habit is what makes the core readable; keep it.

## 3. Findings

Each finding has the evidence, why it costs a newcomer, and a pointer to the refactoring step in section 6.

### 3.1 Architecture and layering (core)

#### A1. Core has no public API and no visible internal boundaries

- `packages/core/src/index.ts:27-61` re-exports every module with `export *`: **406 exported names** in one namespace,
  including test oracles (`FlatRunner`, `IrRunner`), printer internals (`cString`, `cIdentifier`, `pythonClassName`)
  and lowering internals (`simplify`).
- The editor's `main.ts` imports about 70 names from `@ufsm/core` in one import list (`main.ts:4-81`); the CLI imports
  pipeline stages directly (`flatten`, `lowerToIr`, `printIr`).
- Nothing tells a reader which functions are the stable entry points (load, check, generate, simulate, edit) and which
  are implementation details. Every export looks equally important, and every internal change looks like a possible
  break for the editor.

→ Step 5 (subpath exports and an explicit entry list).

#### A2. `v1/` mixes three domains

`v1/` has 20 files that belong to three different concerns:

| Concern | Files | Who uses it |
|---|---|---|
| File format | `model`, `schema`, `parse`, `serialize`, `migrate`, `load`, `options`, `ids` | everyone |
| Diagram layout (derived geometry) | `geometry`, `route`, `action-block`, `sheet`, `labels`, `doc-index` (partly) | editor, check, edits |
| Editing operations (mutations) | `edit`, `create`, `clipboard`, `props` | editor only |
| Validation | `check` (semantic rules **and** layout rules) | everyone |

The folder name says "version 1 of the file format", but most of the code in it is about drawing and editing. A
newcomer looking for "how do transitions follow a moved state" will not look in a folder named after a file format
version. And `check.ts` mixes rules that make code generation wrong (`dangling-ref`, `multiple-initial`) with layout
hygiene (`actions-overlap`, `stale-layout`, sheet fit, `check.ts:292-317`), so semantic validation depends on
`action-block.ts`, `geometry.ts` and `sheet.ts` (`check.ts:10-12`).

Smaller mismatches inside the folder: `props.ts` (meant for "property edits") also holds diagram operations
(`setOffPage`, `setBarOrientation`, `cannotOffPage`, `props.ts:337-407`); `segmentDistance` exists in both
`v1/edit.ts:513` and `editor/src/render.ts:551`.

→ Step 6 (regroup folders; split `check.ts` into semantic and diagram rules).

#### A3. The runtime contract lives inside the interpreter

`InterpreterHost`, `InterpreterOptions`, `InterpreterError`, `busyError` and `BUSY_MESSAGE` are defined in
`interp/interpreter.ts` (lines 26-78) and imported by:

- `semantics/flat-run.ts:12` (a lower layer importing a higher one),
- `ir/eval.ts:12`,
- `backends/python.ts:35` and `backends/ts.ts:36` (for `BUSY_MESSAGE`).

These are not interpreter details: they are the contract every executable form of a machine shares (how the host is
called, which errors exist, what "busy" means). Living in the interpreter, they create the edges
`semantics → interp`, `ir → interp` and `backends → interp`, which make the layer diagram in `index.ts` untrue and
make a reader wonder whether backends depend on the interpreter's behaviour (they do not).

→ Step 3 (move to `runtime/contract.ts`).

#### A4. Shared backend code lives in the C backend; analysis is copied four times

- `CodegenError`, `OUTPUT_NOTICE` and `cIdentifier` are defined in `backends/c.ts:56-83` and imported by
  `python.ts:36`, `ts.ts:37` and `rust.ts:36`; `ts.ts:38` and `rust.ts:37` import `pythonClassName` from the Python
  backend. The C printer is the de facto "common" module, and the TS/Rust printers depend on the Python printer.
- Each printer is a single function: `generateC` (`c.ts:135-856`, ~720 lines), `generatePython` (`python.ts:106`,
  ~500), `generateTypeScript` (`ts.ts:105`, ~500), `generateRust` (`rust.ts:175-1032`, ~860). Everything is a closure
  over local state, so nothing can be read, tested or reused in isolation.
- The same IR analysis opens all four: `walk`, `anyStmt`, `hasQueue`, `hasTerminate`, the reachable-function set, the
  "signal steps only when signals can be queued" rule, the fixed-point `fallible` set, the `signalQueue >= 1` check and
  the `options.trace !== ir.trace` check (`c.ts:143-203`, `python.ts:123-161`, `rust.ts:182-229`, `ts.ts:122-160`).
  Some of these are close to semantic decisions (which step functions are reachable), which the project rule says
  belong in the lowering.
- Each `*OptionsFromTargets` re-implements the same "own keys" switch, and each `*Options` interface re-declares the
  four common options; `generate.ts:78` merges `TsOptions & PythonOptions & RustOptions` into one object.

The cost for a newcomer: to understand one printer you read 700+ lines of nested closures, and to add a fifth language
(C# and Go are on the roadmap) you copy 150 lines of analysis you do not yet understand.

→ Step 4 (`ir/analyze.ts` + `backends/common.ts`, then cut printers into named pieces).

#### A5. Seven executable implementations of the semantics, without a map

The semantics run in the `Interpreter`, the `FlatRunner` (`semantics/flat-run.ts`), the `IrRunner` (`ir/eval.ts`) and
four generated languages. That redundancy is the verification strategy and it is good. But `FlatRunner` and
`IrRunner` live in `src/`, are exported, and are used only by tests (`flat.test.ts`, `ir.test.ts`, `hooks.test.ts`).
A newcomer cannot tell which engine is canonical, which ones ship, and which ones only exist to check a neighbour. The
answer ("the interpreter is the oracle; the flat runner checks the tables; the IR runner checks the lowering; each
backend is checked against the interpreter") is spread over file headers and the progress log.

→ Step 2 (one diagram in `docs/architecture.md`) and Step 5 (keep the oracles out of the public entry point).

#### A6. Text layout is split between core and the editor

The action block was moved into core (`v1/action-block.ts`: monospace cells, derived height, tested). Transition labels
were not: `render.ts:493-533` lays them out with a proportional font, `measureText` and literal offsets (`+40` to the
first line, `+26` to the box top, 20 per line). Core depends on those numbers without saying so: `followTransitions`
uses `was.label.y + 40` to follow "the point where the first line is drawn" (`v1/edit.ts:166`). Hit testing a label
(`render.ts:540`) needs a DOM canvas, and the design rule check cannot measure labels (known issue in plan §8: labels can
stick out of the frame without a warning).

For a newcomer this is a trap: the rule in `.claude/rules/editor.md` says "never measure text in the editor", and the
label code does exactly that, with a magic number in core that only works because of it.

→ Step 7 (move label layout into core the way the action block went).

#### A7. The DocIndex is an implicit cache key

`action-block.ts:252`, `geometry.ts:164`, `sheet.ts:106`, `render.ts:537` and `main.ts:1069` memoize in a `WeakMap`
keyed by `DocIndex`; correctness relies on "a new index after every edit". Mutating functions take a `UfsmDocument`
(an Immer draft) and rebuild an index internally (34 `indexV1` calls in core, 12 in `edit.ts`, 11 in `props.ts`);
queries take a `DocIndex`. That is actually a consistent convention (queries take an index, mutations take a document),
but it is not written down anywhere, and the caching contract ("never mutate a document an index was built from")
is invisible until a stale cache bites.

→ Step 2 (write the convention down) and optionally Step 6 (a `queries`/`mutations` split makes it visible in the folder
layout).

### 3.2 Validation and errors

#### V1. Validity is decided in four places

| Where | Rules | Failure mode |
|---|---|---|
| `v1/check.ts` | ids, names, references, triggers, initials, forks/joins between regions, timers, options, layout | `Diagnostic[]` |
| `semantics/structure.ts` | fork cycles, fork without outgoing (`:228`, `:234`), join sources must be states (`:285`), no trigger into a join (`:286`), initializer has exactly one transition and leads into its region (`:358`, `:362`) | throws `SemanticsError` |
| `semantics/flatten.ts` | no state on the entry path (`:170`), conflicting targets (`:179`), initializer leads to terminate (`:208`) | throws plain `Error` |
| `v1/create.ts` | `cannotConnect`, `cannotAdd` (`:129`, `:217`) | message string for the UI |

Some rules appear twice (`initial-transitions` in check vs `structure.ts:358`; "into a join cannot have a trigger" in
`check.ts:155` and `structure.ts:286`), others only once in a layer that throws. The error classes are
`UfsmFormatError`, `SemanticsError`, `InterpreterError`, `CodegenError` and plain `Error`; the CLI catches three of
them (`cli/src/main.ts:366`). Section 4 shows a concrete consequence.

A newcomer adding a rule has to decide where it goes with no guidance, and a reader trying to answer "can this model
be generated?" has to read four files.

→ Step 1 (one gate: the check runs the structure builder and turns its exceptions into diagnostics).

### 3.3 Editor

#### E1. `main.ts` is a god module

`apps/editor/src/main.ts` is 2,306 lines (88 KB) and holds:

- 30 module-level `let` variables (`doc`, `view`, `tool`, `drag`, `link`, `placing`, `ghost`, `lasso`, `clipboard`,
  `note`, `settings`, `theme`, `panelTab`, `panelFocus`, `panelHighlight`, `previewing`, `recentPicks`, ...);
- the `Doc` interface (`main.ts:154-197`, 22 fields) that mixes the document and undo history, derived data (index,
  diagnostics, tree), view state (page, views, view, selection), simulation state (sim, simError, guards,
  guardsVersion, simOptions, recordActive, hoverEvent, would) and panel state (codeView);
- a global `view` that is "the same object as `doc.view`" (`main.ts:206-207`), i.e. two names for one piece of state;
- file I/O, tabs, settings and theme, search items, the simulator controller, code generation, the menu table
  (`main.ts:832`), the canvas tool state, drag handling, the 100-callback interaction handler (`main.ts:1802-2160`) and
  the `window.ufsm` automation API (`main.ts:2202-2305`);
- 69 manual `requestDraw()`/`updateChrome()`/`renderShell()` calls: every mutation site must remember which parts of
  the screen to refresh.

Why it hurts: there is no place to start reading, no function you can understand without knowing the globals it
touches, and any change risks a missed refresh. It is also the main reason editor behaviour can only be tested through
the 1,649-line Playwright script: none of this logic can be imported by `node:test`.

→ Step 8.

#### E2. Following a key press takes four hops, one through a generated file

To find out what `Delete` does: `fsm/input.ts` maps the key to `EditorFsmEvent.eKey_delete` → `fsm/editor.ufsm`
(41 KB of JSON: 22 states, 51 transitions plus 69 internal ones, 88 actions, 12 guards) decides which state handles
it under which guards → `fsm/editor-fsm.ts` (1,780 generated lines) calls a handler method → the method is one of
100 closures in `main.ts`. The model is the right tool (the editor eats its own dog food, and the interaction logic has
a conformance trace), but it is readable only in the editor itself, and grep cannot connect a key to its effect.

→ Step 9 (generate a key-map table from the model and commit it next to the model).

#### E3. Rendering and hit testing share a module; queries live in the renderer

`render.ts` exports both drawing (`renderPage`) and model queries (`hitTest`, `hitTransition`, `boxSelect`,
`vertexBounds`, `pageBounds`, `pillAt`, `labelBox`). The queries are what the interaction code needs; the drawing is
not. Keeping them together means hit-test logic cannot be unit-tested without a canvas, and it hides that `labelBox`
is the only query that needs the DOM (A6).

→ Step 8 (move queries to `hit.ts`; after Step 7 they need no DOM).

### 3.4 Naming and vocabulary

#### N1. "Trace" means four things

| Name | Meaning |
|---|---|
| `Trace`, `TraceStep`, `runTrace`, `tests/traces/*.json` | a conformance test case: steps and expected calls |
| `TraceEntry`, `onTrace` (`interpreter.ts:35`, `:55`) | an observable step the interpreter reports (enter, exit, call, ...) |
| `trace` option, `TRACE_KINDS`, `<prefix>trace()` (`ir.ts:63`) | the hook generated code calls for the application |
| `docs/live-trace.md` | a planned on-target recording |

Plus `traceText`, `saveTrace`, `formatTrace` in the editor and CLI, which mean the first. In one function a reader can
meet two of them (the simulator records a conformance `Trace` from interpreter `TraceEntry` events).

#### N2. Synonyms and private words

- **page vs sheet**: core says sheet (`sheetOfRegion`), the editor says page and aliases it
  (`nav.ts:13-14`: `pageOfRegion = sheetOfRegion`); the format says "off-page region".
- Words a newcomer must learn without a glossary: *slot*, *offer*, *candidate*, *domain*, *blocks*, *settle*,
  *microstep*, *initializer*, *compound transition* (semantics); *jog*, *S route*, *free route*, *band*, *pill* (the
  hidden-lines marker), *grip*, *ghost* (diagram/editor). Most are defined, but each in the one file that introduces
  it.

→ Step 2 (glossary) and Step 10 (renames).

### 3.5 Documentation and onboarding

#### D1. The architecture is documented for Claude, not for people

- The only architecture overview and file map are in `.claude/CLAUDE.md` and `.claude/rules/{editor,backends}.md`.
  They are dense, written as instructions to an agent, and live in a hidden folder.
- The reasons behind decisions are in `.claude/rework-decisions.md` (66 KB) and the history in `.claude/rework-log.md`
  (65 KB). Valuable, but nobody new reads 130 KB to learn why things are the way they are.
- `README.md` covers setup, controls and status; it has a layout table but no picture of how the parts fit together.
- There are no recipes for the three changes a newcomer is most likely to make: add a design rule, add an editor
  command or key, add a backend option (or a backend).

#### D2. Some files are hard to read for reasons a tool would fix

- No formatter and no linter. 173 hand-written lines are longer than 160 characters (e.g. `flatten.ts:228`, a nested
  ternary on one line; `c.ts:329`, a block-bodied lambda inside a `map` inside a template); `main.ts` has 62 lines over
  120. Density is a choice, but without a formatter it varies by file.
- No tool enforces the layering rules (core is platform neutral, backends do not import each other, editor reaches the
  host only through `platform.ts`). Today they hold because one careful person writes all the code.

→ Step 2 and Step 11.

### 3.6 Tests

#### T1. Four parallel backend suites

`backend-{c,python,ts,rust}.test.ts` share the same outline: conformance traces; "matches the interpreter" on joins,
expression forms, repo models, random models, debug+trace, small queues; "generated files" for determinism, name
clashes, `targets.<x>` parsing and "only what the model uses". Each has its own harness (`c-harness.ts` 377 lines,
`py-harness.ts` 272, `rust-harness.ts` 352, `ts-harness.ts` 121). The parallel structure is a strength, but it is
maintained by copying, so the four suites have already drifted (only Rust tests the keyword model in the differential
pass; only Python, TS and Rust test hand-built IR expression shapes; C does not).

→ Step 12 (one backend contract suite, parameterized).

#### T2. One 1,649-line browser script

`apps/editor/test/browser/check.mjs` (122 KB) is the only test of editor interaction. It is sequential, so a failure
early on can hide everything after it, and it cannot be run by area. Most of what it checks would be unit tests if
`main.ts` were split (E1).

## 4. Correctness issue found along the way

**`ufsm check` accepts a model that `ufsm generate` then crashes on.** A transition into a fork that has no outgoing
transitions passes the design rule check, and `buildStructure` throws `SemanticsError`, which the CLI does not catch, so
the user gets a Node stack trace:

```
$ npm run -s ufsm -- check fork.ufsm
OK (0 warnings)
$ npm run -s ufsm -- generate c fork.ufsm -o build
C:\...\packages\core\src\semantics\structure.ts:234
      if (outs.length === 0) throw new SemanticsError(`fork '${to.name}' has no outgoing transitions`, to.id);
```

The same holds for the other `SemanticsError` and plain `Error` throws listed in V1 (fork cycles, flattener path
errors). In the editor the simulator and code preview catch any error, so it shows as a message there, but the Problems
panel stays green. The `Interpreter` constructor has the same gap: it turns check errors into
`InterpreterError("invalid-model")` but lets `SemanticsError` through.

Fix: Step 1. Add a trace-free unit test per throw site: "a model with this defect gets a diagnostic, and
`generateFiles` raises `CodegenError`, never anything else".

8. "The architecture doc is in `.claude/`, and the reasons are in a 66 KB table." (D1)

## 6. Refactoring plan

Ordered so that each step lands on its own, keeps CI green, and makes the next one easier. Effort: S = under a day,
M = a few days, L = a week or more. None of the steps changes generated code or the file format.

### Step 1: one validity gate (S, fixes section 4)

- In `checkV1`, after the existing rules and only when there are no errors so far, call `buildStructure` and
  `flatten` inside a `try` and turn `SemanticsError` (and the flattener's errors, after giving them a class) into
  `Diagnostic`s with stable codes (`fork-no-outgoing`, `fork-cycle`, `join-source`, ...). The `id` on `SemanticsError`
  already says where to point.
- Better still, move each structural rule into `check.ts` proper and keep the throws in `structure.ts` as asserts with
  a comment "unreachable after checkV1". This is the cleaner option for the long term: calling `buildStructure` from
  `checkV1` adds an import from `v1/` into `semantics/`, which today imports `v1/`, so the first option is a stopgap
  (or lives in a small `check/runnable.ts` above both layers).
- Remove the duplicated rules (initializer count, trigger into join) from one side.
- Give `flatten.ts` a proper error class, or make its throws asserts.
- Make `modelIr` and the `Interpreter` constructor rely on the gate only; the CLI then never sees anything but its
  three known error classes.
- Rule of thumb to write down: **`checkV1` without errors ⇒ every later stage succeeds.** Add a test that runs the
  random-model generator with mutations (drop a transition, retarget into a fork) and asserts that either `checkV1`
  reports an error or `generateFiles` succeeds for every target.

### Step 2: human documentation (S–M)

- `docs/architecture.md`: the pipeline diagram from plan §4, the layer list with the allowed import directions, the
  seven engines and who checks whom (A5), the editor's data flow (input → FSM → handler → core edit → history →
  refresh → render), and the conventions that today live only in `.claude/` (platform neutrality, queries take a
  `DocIndex` and mutations a document, the caching contract from A7, "backends make no semantic decisions").
- `docs/glossary.md`: every term from N1/N2 with a one-line definition and the file that owns it.
- Three recipes in `docs/contributing.md`: add a design rule, add an editor command (menu + key + FSM + handler), add a
  backend option.
- Shrink `.claude/CLAUDE.md` to pointers into these files so there is one source; agents and people then read the same
  thing.
- Add a 10-line summary at the top of `rework-decisions.md` of the decisions that shape the code today, with links to
  the rows.

### Step 3: move the runtime contract out of the interpreter (S)

Create `core/src/runtime/contract.ts` (or `semantics/runtime.ts`) holding `MachineHost` (today `InterpreterHost`),
`RunOptions`, `MachineError` + its codes, `busyError`, `BUSY_MESSAGE`, and the `TraceMachine` interface from
`interp/trace.ts`. Interpreter, flat runner, IR runner, trace runner and the backends import from there. Keep the old
names as type aliases for one release if the editor uses them. Afterwards the only arrows into `interp/` come from the
CLI, the editor and tests, and the layer list in `index.ts` is true.

### Step 4: a shared backend layer (M)

1. `ir/analyze.ts`: one function `analyzeIr(ir, { maxMicrosteps })` returning
   `{ hasQueue, hasTerminate, hasTimers, reachable: Set<string>, fallible: Set<string>, eventSteps, signalSteps }`,
   plus `walkStmts`. Unit-test it once. Every printer calls it instead of its own copy. Consider moving the
   reachability decision ("signal steps only when signals are queued") into the lowering, so the IR simply does not
   contain unreachable functions; that matches the project's own rule.
2. `backends/common.ts`: `CodegenError`, `OUTPUT_NOTICE`, `identifier()` (today `cIdentifier`), `pascalCase()` (today
   `pythonClassName`), `checkTraceMatches(ir, options)`, and a generic `readTargetOptions(doc, target, schema)` that
   replaces the four hand-written `*OptionsFromTargets` switches.
3. A `ResolvedOptions` type computed once in `generate.ts` (`signalQueue`, `maxMicrosteps`, `debugInfo`, `trace`), passed
   to every printer next to its own target options, so the four `*Options` interfaces stop re-declaring the common ones.
4. Then, per printer, cut the one big function into named parts that take an explicit context object: `names` (identifier
   allocation and clash check), `exprPrinter`, `stmtPrinter`, `emitHeader`/`emitApi`, `emitRuntime` (reset, process,
   settle), `emitDebugInfo`. This can be done one backend at a time; the generated output must stay byte-identical (the
   existing tests and a golden diff of every repo model guard that).

Payoff: a new backend starts from about 300 lines of language-specific printing instead of 700 lines of copied
analysis, and a reader can study the statement printer without the header generator.

### Step 5: give core a public surface (S–M)

- Replace `export *` in `index.ts` with explicit exports grouped by purpose, or add subpath exports in
  `packages/core/package.json`: `@ufsm/core` (load, serialize, check, generate, Interpreter, traces), `@ufsm/core/diagram`
  (geometry, route, action block, sheet), `@ufsm/core/edit` (edit, create, clipboard, props), `@ufsm/core/pipeline`
  (structure, flatten, IR: what the CLI's `flatten`/`ir` commands and tests need).
- Do not export `FlatRunner`, `IrRunner` and `simplify` from the main entry; tests import them by path.
- Mark the rest internal (a leading comment, or `@internal` with `stripInternal` if a declaration build ever exists).

The editor's 70-name import then splits into three or four short, meaningful ones, and the question "may I use this?"
has an answer.

### Step 6: regroup core folders by domain (M, mostly mechanical)

Suggested layout (names are a proposal; the split matters more than the names):

```
core/src/
  format/      model, schema, parse, serialize, migrate, load, options, ids      (the file format, v1 and v0 reading)
  model/       doc-index, labels (text of triggers/guards/actions)               (queries over a document)
  diagram/     geometry, route, action-block, label-layout (step 7), sheet       (derived layout, read-only)
  edit/        layout (today edit.ts), create, clipboard, props                  (mutations on a draft)
  check/       semantic.ts, diagram.ts, index.ts (checkV1 = both)                (design rule check)
  semantics/   structure, flatten
  runtime/     contract (step 3)
  interp/      interpreter, trace
  ir/          ir, lower, simplify (split out of lower.ts), analyze (step 4), ids, print
  backends/    common, c, python, ts, rust, generate
  verify/      flat-run, ir eval                                                 (oracles; not in the public entry)
```

Rules that fall out and can be enforced (Step 11): `format` imports nothing else; `diagram` and `check/semantic` import
only `format` and `model`; `edit` may import `diagram`; `semantics` never imports `diagram`; `backends` never import each
other or `interp`. Move `setOffPage`/`setBarOrientation`/`cannotOffPage` from `props.ts` to the layout edits, and keep
one `segmentDistance` in `diagram/`.

Do this in one commit per folder with `git mv` so history follows, and keep `v0/` as is.

### Step 7: label layout in core (M)

Do for transition labels what E-AB did for the action block: `diagram/label-layout.ts` computes items, lines and the
box from the label width on a character grid (or from an injected `measure(text) => width` that defaults to a
monospace cell), and exports the line offsets as named constants. `render.ts` draws it; `edit.ts` uses the constant
instead of `+ 40`; `labelBox` and hit testing no longer need a DOM canvas; the sheet fit check can include labels (closes
the known issue in plan §8). If changing the label font is not wanted, the injected-measure variant keeps today's look
and still moves the logic and the constants into one tested place.

### Step 8: split the editor's `main.ts` (L, in slices)

Target: no file over ~500 lines, no module-level mutable state outside one store, and the editor logic importable from
`node:test`.

1. **`DocSession` class** (`session.ts`): today's `Doc` fields, with methods `edit(recipe)`, `undo()`, `redo()`,
   `begin()/preview()/commit()/cancel()`, and `refresh(recheck)`. Split its fields into `document` (history, index,
   diagnostics, tree, file info), `view` (page, views, view, selection) and `sim` (simulation, guards, options,
   hover, would). Remove the global `view` alias.
2. **`Workspace`** (`workspace.ts`): the list of sessions, the active one, the clipboard, and an event emitter with a
   small set of change kinds (`document`, `selection`, `view`, `sim`, `chrome`). Replace the 69 manual refresh calls by
   `workspace.changed(kind)`, and let one scheduler decide what to redraw (canvas on `document|selection|view|sim`,
   shell on `document|selection|chrome`, ...). This removes the "forgot to call `updateChrome()`" class of bugs.
3. **`canvas/` controller**: tool state (`tool`, `horizontal`, `ghost`, `placing`, `link`, `drag`, `lasso`,
   `pressGrip`) plus the FSM handler, split by the editor model's regions: `pointer.ts` (select, lasso, pan, zoom,
   drag), `tools.ts` (place, link), `keys.ts` (jump, edit and add maps). Each exports a part of `EditorFsmHandler`; the
   full handler is their spread. Most of these parts can then be unit-tested against a `Workspace` with a fake canvas
   transform.
4. **`commands.ts`**: one table of commands (id, label, keys, enabled, run). The menus (`MENUS`), the command palette
   (`menuCommands` in search) and the FSM's key actions all look up the same entries, so a command has one definition.
5. **`files.ts`** (open, save, save as, new, close with confirmation), **`settings-controller.ts`** (settings, theme,
   zoom, preview), **`sim-controller.ts`** (start, stop, step, would-map, trace saving), **`search-items.ts`**
   (element/setting/project rows), **`automation.ts`** (`window.ufsm`, which then only calls public methods of the
   workspace).
6. Move model queries out of `render.ts` into `hit.ts` (E3).
7. Split `panel.tsx` (1,312 lines) along its tabs: `properties/` (State, Pseudo, Transition, Internal, Timer props and
   the list widgets), `project.tsx`, `problems.tsx`; `panel.tsx` keeps only the tab strip.

Order: 1 → 2 → 5 (low risk, moves code) → 3 → 4 → 6/7. After step 2 the browser check can be split by area (T2)
and much of it replaced by `node:test` suites over the workspace.

### Step 9: make the interaction model greppable (S)

Generate `apps/editor/src/fsm/KEYMAP.md` from `editor.ufsm` (a small CLI command or a test helper): one row per
transition and internal transition with state path, event (key), guards and actions, grouped by region; the freshness
test that already guards `editor-fsm.ts` also guards this file. With commands from Step 8.4, the action names map
one-to-one to command ids, so a key can be followed from the table to the command with one grep. Add a paragraph to
`docs/architecture.md` on why the editor uses its own state machine.

### Step 10: vocabulary (S, do with Step 2)

- Rename interpreter `TraceEntry`/`onTrace` to `StepEvent`/`onStep` (or `ExecutionEvent`). Keep "trace" for
  conformance traces (`Trace`, `TraceStep`) and the generated hook (`trace` option), and name the planned feature
  "live recording" or keep "live trace" but say in the glossary which one it is.
- Pick one of page/sheet. Core and the format already say sheet; rename the editor's `page*` helpers and drop the
  aliases in `nav.ts`.
- Rename `pill` to `hiddenMarker` (or similar) in core and editor; it is the one term nobody can guess.

### Step 11: tooling that keeps the structure (S)

- Add a formatter (Prettier with `printWidth: 120`, or dprint) and format the hand-written TypeScript once, in its own
  commit, with the commit listed in `.git-blame-ignore-revs`. Generated files and `old/` excluded.
- Add an import-boundary check (`dependency-cruiser`, or ESLint with `no-restricted-imports` per folder) encoding the
  rules from Step 6 and the existing ones (no Node/DOM in core, host access only through `platform.ts`, backends do not
  import each other). Run it in CI next to `typecheck`.

### Step 12: one backend contract suite (M)

`test/backend-contract.ts` exports `describeBackend(spec)` where `spec` gives the language name, a harness
(`generate`, `build`, `run traces`, `run differential`), skip conditions, and the language-specific extras (keyword
model, type checker, linter). The shared cases (traces, joins, expression forms, repo models, random models,
debug+trace, small queue, hand-built IR, determinism, "only what the model uses", `targets.<x>` parsing, timer API
presence) are written once; each `backend-*.test.ts` shrinks to the spec plus its truly language-specific tests. This
also removes the drift noted in T1, and gives a new backend a ready checklist.

## 8. Things I would not change

- **The lowering as one function.** `lowerToIr` (`lower.ts:21-310`) is long, but it is one coherent algorithm with a
  clear header; splitting it by helper would scatter the reasoning. Moving the IR simplifier (`lower.ts:312-527`) into
  `ir/simplify.ts` is enough.
- **The interpreter's style.** It is deliberately unoptimized and reads like the spec; keep it that way.
- **The redundant engines.** `FlatRunner` and `IrRunner` look like dead code to a newcomer, but they localize failures
  to one pipeline stage. Document and fence them (Steps 2, 5); do not delete them.
- **The editor's own uFSM model.** It is extra indirection, but it is the best test of the product and it gives the
  interaction logic a trace. Make it greppable (Step 9) rather than replacing it.
- **Comment density.** Some lines are long, but the comments are accurate and say why. A formatter will fix the
  layout; the habit of explaining is worth more than brevity.
