# C# backend

`ufsm generate csharp` turns a model into one C# source file
(`<Class>.cs`). It needs C# 8 or newer (it turns on nullable reference
types for itself) and nothing beyond `System`, which it always writes as
`global::System`, so the `using` directives and implicit usings of a project
cannot change what it means. It starts with `// <auto-generated/>`, has an
XML doc comment on every public member and builds without warnings at the
highest warning level with `GenerateDocumentationFile` and warnings as
errors; with the marker removed it also passes the .NET analyzers'
recommended set, apart from the naming rules (the names are the model's).

Behaviour is defined by [semantics.md](semantics.md); the generated code is
a direct print of the IR (`ufsm ir <model>`), the same IR the
[C](backend-c.md), [C++](backend-cpp.md), [Python](backend-python.md),
[TypeScript](backend-ts.md), [Rust](backend-rust.md) and [Go](backend-go.md)
backends print, and it is tested against the reference interpreter.

The generated code may be used under any terms ([output exception](../LICENSE-EXCEPTION)); uFSM itself is GPL-3.0-or-later.

## Generating

```sh
npm run ufsm -- generate csharp examples/dimmer.ufsm -o build/
# wrote build/Dimmer.cs
```

The model must pass `ufsm check` without errors. Settings come from the
model's `targets.csharp` section and can be overridden on the command line:

| `targets.csharp` key | Flag | Default | Meaning |
|----------------------|------|---------|---------|
| `className` | `--class-name` | model name in PascalCase (`test_guard1` → `TestGuard1`) | Machine class; also names `<Class>Event`, `I<Class>Handler`, `<Class>Exception`, ... |
| `namespace` | | none (the global namespace) | Namespace of every type, dotted (`Home.Lights`) |
| `file` | | the class name | File name: `<file>.cs` |
| `out` | `-o` | current directory | Output folder, relative to the model's file or absolute ([targets](format-v1.md#targets)) |

Unknown keys, and the behaviour options below, are reported as warnings and ignored there.

The model's [`options`](format-v1.md#options) section sets what every target
shares; the flags override it for one run:

| `options` key | Flag | Default | Meaning |
|---------------|------|---------|---------|
| `signalQueue` | `--signal-queue` | 16 | Capacity of the signal queue (only generated if the model emits signals) |
| `maxMicrosteps` | `--max-microsteps` | 10000 | Microsteps per `Reset`/`Process` call before a `livelock` error; 0 removes the check |
| `debugInfo` | `--debug-info` | false | Names and an is-active query ([Debugging](#debugging)) |
| `trace` | `--trace` | false | A trace hook the handler implements ([Debugging](#debugging)) |

`signalQueue` and `maxMicrosteps` change behaviour, so they are set in
`options` only, never per target: a model behaves the same in every language
and in the simulator, queue overflows included. `debugInfo` and `trace` change
only the generated API, so `targets.csharp` may override them for this language.

## Generated API

For `examples/dimmer.ufsm`:

```csharp
public sealed class DimmerException : System.Exception
{
    public string Code { get; } // "queue-overflow", "livelock", "unknown-event", "not-started", "busy"
}

public enum DimmerEvent { eButton = 0, eOffButton = 1 }

public interface IDimmerHandler
{
    void lamp_off();
    void lamp_10_percent();
    // ... one method per action; guards: bool <guard>();
}

public sealed partial class Dimmer
{
    public Dimmer(IDimmerHandler handler); // keeps the handler; runs nothing yet
    public void Reset();                   // start, or restart; no exit actions run
    public void Process(DimmerEvent @event);
}
```

- The handler is any class that implements `I<Class>Handler`: one method per
  action and guard, named as in the model (a C# keyword as a verbatim
  identifier: `@event`). Guards return a `bool`. They may be called more
  than once per event and in any order, so they should not have side
  effects. An action or guard named like a member every object has
  (`ToString`, `Equals`, ...) or like a handler method uFSM adds
  (`TimerStart`, `TimerStop`, `Trace`) is refused.
- The constructor does not start the machine, so the handler can keep a
  reference to it before the first entry action runs. Call `Reset()` first;
  `Process()` before that throws `not-started`.
- Errors throw `<Class>Exception` with the interpreter's error code in
  `Code`. After an error the machine is in an undefined state until
  `Reset()`, and `Process()` throws `busy` until then.
- An exception thrown by an action or guard is not caught: it passes through
  `Reset()`/`Process()` unchanged and leaves the machine half-way. Until the
  next `Reset()`, `Process()` then throws `busy`, as it does when an action
  or guard calls `Process()` itself (that nested call changes nothing; the
  outer call goes on). See
  [Failed and nested calls](semantics.md#failed-and-nested-calls).
- A machine is not thread-safe: call it from one thread, or lock around it.
- The class is `partial`, so an application can add members in a file of
  its own. Everything `private` (`cfg`, `step_eButton`, ...) is internal and
  may change between uFSM versions.
- Signals are internal: actions emit them, and `Process` runs them (FIFO)
  after the event until the queue is empty. `queue-overflow` means more
  than `signalQueue` signals were waiting at once.
- After a terminate pseudo-state is reached, `Process` does nothing until
  `Reset()`.
- The machine allocates its arrays once, in the constructor; `Reset()` and
  `Process()` allocate nothing (an error allocates its exception).

## Timers

A model with [timers](format-v1.md#timers) gets a timer enum, two more
handler methods and `<Class>.TimerEvent()`, the event to process when a
timer expires (none of this without timers). For `door` with timers
`travel` and `poll`:

```csharp
public enum DoorTimer { travel = 0, poll = 1 }

public interface IDoorHandler
{
    void TimerStart(DoorTimer timer, uint ms, bool periodic);
    void TimerStop(DoorTimer timer);
    // ... actions and guards
}

public static DoorEvent Door.TimerEvent(DoorTimer timer);
```

A handler can keep one `System.Threading.Timer` per timer and post the
expiry to the thread that runs the machine. The contract, as in every
language:

- Stopping a timer that is not running does nothing.
- A periodic timer is started once; the application re-arms it every period.
- After a stop returns, no expiry of the earlier start should be delivered.
  One that is already queued arrives as an ordinary event and is handled as
  such (in a state that does not react to it, nothing happens).
- Start and stop run inside `Reset()` and `Process()`: they must not block or
  call the machine. `Reset()` stops every timer first, whatever runs.

## Debugging

Always generated: `<Class>State` (normal and final states in document order,
named after the states; a name that repeats is qualified with its parent
states, and free text is made an identifier: `10%` becomes `s10_`) and the
model's fingerprint, which identifies how events, signals, states and
transitions are numbered (`ufsm info` prints it for a model file; see
[Numbering and trace hooks](semantics.md#numbering-and-trace-hooks)).

```csharp
public enum DimmerState { Off = 0, On = 1, s10_ = 2, /* ... */ }
public const uint Fingerprint = 0xc57ac6eau; // in Dimmer
```

With `debugInfo`, the machine class gets the names as in the model, by
number, and an is-active query:

```csharp
public static IReadOnlyList<string> EventNames { get; }
public static IReadOnlyList<string> SignalNames { get; }
public static IReadOnlyList<string> StateNames { get; }
public static IReadOnlyList<string> TimerNames { get; } // when the model has timers
public bool IsActive(DimmerState state);
```

With `trace`, `<Class>TraceKind` (`Event`, `Signal`, `Transition`, `Enter`,
`Exit`) and one more handler method, called with ids only (the transition
numbers are listed in a comment in the class; a `<Class>Signal` enum is
generated when the model has signals):

```csharp
void Trace(DimmerTraceKind kind, int id);
```

It runs inside `Reset()` and `Process()`, so it must not block or call the
machine.

## Example

```csharp
using System;

internal sealed class Lamp : IDimmerHandler
{
    public int Percent { get; private set; }

    public void lamp_off() => Percent = 0;
    public void lamp_10_percent() => Percent = 10;
    public void lamp_30_percent() => Percent = 30;
    public void lamp_50_percent() => Percent = 50;
    public void lamp_100_percent() => Percent = 100;
}

internal static class Program
{
    private static void Main()
    {
        var lamp = new Lamp();
        var machine = new Dimmer(lamp);
        machine.Reset(); // Off
        machine.Process(DimmerEvent.eButton); // On, 10%
        machine.Process(DimmerEvent.eButton); // 30%
        machine.Process(DimmerEvent.eOffButton); // Off
        machine.Process(DimmerEvent.eButton); // On again: history restores 30%
        Console.WriteLine($"lamp at {lamp.Percent}%"); // lamp at 30%
    }
}
```

## Inside the generated file

The machine class starts with a table of regions and their states (the
value of `cfg[region]` for each state). Its private methods are the IR
functions: `enter_rN`, `exit_rN`, `record_rN`, `restore_rN`,
`step_<event>` / `step_<signal>` / `eventless` (one microstep; they return
whether one ran) and `Settle`. Errors are exceptions, so no return codes
are passed around.

## Testing

`packages/core/test/backend-csharp.test.ts` builds the generated files with
the .NET SDK and runs them against the same scripts as the interpreter. It
skips without an SDK (`$DOTNET`, else `dotnet` on `PATH`, else the per-user
install of `dotnet-install` in `%LOCALAPPDATA%\Microsoft\dotnet` or
`~/.dotnet`); CI sets `UFSM_REQUIRE_DOTNET` so a missing SDK fails instead.
It checks that:

- all conformance traces in `tests/traces/` pass (including an action that
  throws and one that calls `Process()` on its own machine);
- on random event sequences (with random guard values), every repo model,
  300 random models (`UFSM_CSHARP_RANDOM=<n>` for more), the debugInfo +
  trace hooks, 100 random models with a 2-slot queue and a hand-built IR
  covering every expression shape call exactly the same actions, end in the
  same states and fail with the same errors as the reference interpreter;
- every repo model and 40 random models, with and without `debugInfo` and
  `trace`, build with warnings as errors at warning level 9999, nullable
  on, XML docs required and the analyzers' recommended set (without the
  naming rules CA1707, CA1708, CA1716 and CA1720);
- a handler that misses an action does not compile;
- the example above prints `lamp at 30%`.
